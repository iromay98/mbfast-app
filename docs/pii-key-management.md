# 個人情報の暗号化鍵の管理（mbPIT 施工証明書）

**この鍵を失うと、証明書と法定記録簿に車台番号・登録番号を出力できなくなり、
2年間の保存義務（道路運送車両法 第91条）を果たせなくなります。**
技術的な不便ではなく事業継続の問題として扱ってください。

## 何の鍵か

| 用途 | 環境変数 | 失った場合 |
|---|---|---|
| 車台番号・登録番号の暗号化（AES-256-GCM） | `PII_ENC_KEYS` | 証明書・法定記録簿に車台番号を出力できない（**復旧不能**） |
| 車両の一意キー生成（HMAC-SHA256） | `SERVER_SECRET` | マイカーページ・施工証明書の照合が全て切れる（**復旧不能**） |

2つは**別の鍵**です。`SERVER_SECRET` から `PII_ENC_KEYS` を導出してはいけません
（片方の漏洩がもう片方に波及するため）。

## 設定形式

```
PII_ENC_KEYS="k2:<32バイト以上の乱数>,k1:<旧鍵>"
```

- 先頭が**現行鍵**（新しい暗号化はこれを使う）
- カンマ区切りで**旧鍵を併記**できる（旧鍵で暗号化された既存データを読むため）
- 暗号文は `v2:<keyId>:<iv>:<tag>:<data>` の形式で、どの鍵で暗号化したかを保持する

鍵の生成:

```bash
openssl rand -base64 48
```

## 保管とバックアップ（必須）

1. **本番の値は VPS の `/root/mbfast-app/.env` にのみ置く**。リポジトリ・DB・チャット・
   スクリーンショットに残さない
2. **オフラインの控えを2箇所以上**に保管する（例: パスワードマネージャ＋紙で金庫）。
   鍵はDBのバックアップと**別の場所**に保管する（同じ場所だと同時に失う）
3. DBのバックアップを取るときは、**その時点の鍵IDも記録**しておく
   （復元したDBを読むにはその鍵が必要）
4. 担当者が1人だけの状態を作らない（引き継ぎ不能になる）

## 復旧手順

1. `/root/mbfast-app/.env` の `PII_ENC_KEYS` を確認する
2. 失われている場合、オフライン控えから該当 `keyId` の鍵を復元して `PII_ENC_KEYS` に**追記**する
   （現行鍵を消さない。旧鍵は末尾に足す）
3. `docker compose -f /root/mbfast-app/docker-compose.prod.yml up -d` で再起動
4. 証明書を1件開き、車台番号が表示されることを確認する
5. 復元できない場合: 影響範囲を `PitPiiAccessLog.keyId` と `PitCertificate` の作成日から特定し、
   該当車両の車台番号は**車検証から再入力**する（暗号文からの復元は不可能）

## 鍵のローテーション

1. 新しい鍵を採番して先頭に追加: `PII_ENC_KEYS="k3:<新>,k2:<現>,k1:<旧>"`
2. アプリを再起動（新規の暗号化は k3 で行われる）
3. 既存データの再暗号化は `needsRekey()` で対象を抽出して順次実施（再暗号化は監査ログ対象外）
4. 旧鍵は、対象データが残っていないことを確認してから削除する

## 復号の監査

車台番号・登録番号の復号は `PitPiiAccessLog` に記録されます（誰が・どの証明書の・何を・なぜ）。
記録されない復号経路は実装できない構造です（`decryptPiiAudited` が引数でアクセス文脈を要求する）。
不審なアクセスの調査は次のクエリで行えます。

```sql
SELECT "at", "actorUserId", "actorRole", field, purpose, "certificateId", ok
FROM "PitPiiAccessLog" ORDER BY "at" DESC LIMIT 100;
```
